# Software tests: false safety

A green suite is a claim: nothing relied on is broken. A test that cannot fail, or whose failure
would change nothing, makes that claim without evidence. This page gives the principle, a catalog
of cases that illustrate it, the signs a suite is exploding, the check that detects both, and the
self-review that applies it per role.

## The principle

A test is **tautological** when no plausible wrong implementation makes it fail, or when it
restates its own input. It reassures and protects nothing, and it is worse than no test, because
it spends maintenance and buys false confidence.

A test is **trivial** when it can fail but its failure would change no decision: it checks
something nobody relies on, something a framework already guarantees, or something a stronger test
already catches. Trivial tests are harmless one at a time and costly in bulk: they are the suite
growing without becoming more useful.

The two questions that sort any test: *what wrong implementation would turn this red?* and *if it
turned red, what would someone do differently?* A good guard answers both. A confirm answers them
for a few days. A tautology has no answer to the first; a trivial test has none to the second.

## Catalog

This is a sample of cases, chosen to teach the principle. Each fails the principle for a reason
that applies well beyond it. Use the reason, not the label.

- **Mirror test.** The expected value is produced by the same logic as the code (a copied
  formula, or calling the function and asserting equality with itself). The test cannot disagree
  with the code, so a wrong formula passes. Cure: derive the expectation independently, by hand,
  from an oracle or as a property.
- **Mock echo.** The test configures a mock to return X, runs code that returns what the mock gave,
  and asserts X. It verifies the mock's script. Cure: use the real collaborator where we own it;
  where it is outside our control, test the code's *decision* about the response (what it does
  with a 429), not that the response was passed through.
- **Set-then-get.** Assign a value, read it back, assert equality. It passes for any plain
  storage and fails only if the language is broken. It becomes meaningful only when something
  between set and get could transform the value (validation, normalization, persistence). Then
  the guard targets that transformation.
- **Shape-only or not-None assertion.** `assert result is not None`, `len(items) > 0`, or "returns
  a dict". Almost any wrong implementation satisfies it. Assert the content that matters for the
  consumer, for at least the fields the consumer reads.
- **Unreviewed snapshot.** A recorded output compared on every run, generated by the code and
  accepted without reading. It guards "the output is what it was", including its bugs, and is
  regenerated whenever it fails, so the failure carries no information. A snapshot reviewed
  line by line against an independent expectation is a different thing.
- **Framework self-test.** Tests that the ORM saves, the router routes, the language sorts. That
  behavior belongs to its maintainers' suite, and failing here would mean the dependency is
  broken, which is a probe's question at most.
- **Assertion-free run.** The test calls the code and asserts nothing, or only that it did not
  throw. It proves the code can run, which a compiler or smoke check already shows, and passes
  when the result is wrong. Add an assertion on the outcome, or delete it.
- **Test never seen failing.** A test written after the code and never red. It may be unable to
  fail (wrong target, over-broad mock, assertion that is always true), and nothing so far has
  shown otherwise. Cure: break the code on purpose and see it fail.

None of these is a rule to match against. Each is one instance of "cannot fail" or "changes
nothing". Look for the case the list does not name: a test whose setup already guarantees its
assertion; a parameterized test whose rows all fall in one class; a test of a constant; a test
that passes on an empty database because it loops over nothing; a guard that duplicates, one scope
up, what a lower guard already proves. If a test cannot say what bug it catches, treat it as
suspect whatever it looks like.

## Signs of explosion

The suite is growing in volume faster than in protection when you see:

- tests enumerated per function or per branch, instead of per behavior;
- permutations of inputs that probe no distinct behavior (many rows in one equivalence class);
- one test per incident, each reproducing a bug, with no guard for the behavior behind them (see
  `software-planning.md`);
- a code-to-test ratio, a coverage percentage or a test count used as a goal. Whatever is made
  the target stops measuring the thing it stood for: coverage is reached by tests that execute
  lines and assert nothing;
- confirms still present after their guard passed, or unmarked so nobody can tell;
- a growing suite that fails often and for unrelated reasons, a sign that tests are coupled to
  internals rather than behaviors.

The response is never to cap the size. Apply the distinct-failure rule: for each test, name the
plausible bug it catches that the others miss, and remove or merge what cannot.

## The mutation check

The detector for both tautological and trivial tests is to **make the plausible bug and see red**.
Name a wrong implementation a human or an agent could realistically write, or inject one: invert a
condition, return a constant, drop a boundary check, swap an argument, skip a call. Run the test.
If it stays green, it did not guard that behavior: strengthen it, move it to the right scope, or
delete it.

Do it by hand on the guards that carry weight (the cornerstones above all); a minute per guard is
cheap against false safety. Automated mutation tools can run it at scale and are optional: they
are not required, and their surviving mutants need judgement, since some mutations change nothing
observable.

The **ownership check** is the special case. Before keeping a test for new or changed code, remove
or break that code. If the test still passes, it does not belong to this change: it tests
something else or nothing. Run it as part of seeing a guard red.

## Self-review

Run this before a plan or a change is finished, with the roles in mind. The questions are about
each test's purpose, not boxes to tick.

- **Each guard** states its expected behavior, its scope and the reason for that scope, and the
  bug it catches. Could a plausible wrong implementation pass it? Was it seen failing? Does it go
  through the consumer's interface, so it survives refactors?
- **Each confirm** names the guard it serves and is marked so it can be culled. Is the guard now
  green? Then the confirm goes, or is promoted and rewritten to guard standards.
- **Each probe** names its question and the decision it feeds. Is it answered? Then the answer is
  recorded and the probe is deleted, or it became a boundary guard.
- **The suite as a whole:** for any two tests on the same behavior, which distinct failure does
  the second catch? What was deliberately left untested, and is that written down?

Revise whatever fails a question before moving on. Then ask what kind of false safety this review
has not looked for, in this project, and look for that.
